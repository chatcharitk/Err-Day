# บันทึกรายจ่ายและค่าตอบแทน: ผลตรวจและการเปลี่ยนแปลง

ตรวจจากโค้ดและฐานข้อมูลที่ตั้งค่าในโครงการ เมื่อ 14 กันยายน 2569 การตรวจข้อมูลจริงเป็นการอ่านเท่านั้น ยังไม่รัน migration หรือแก้รายการเงินจริง

## ผลตรวจข้อมูลเดิม

| รายการ | จำนวน | ความหมาย / วิธีจัดการ |
|---|---:|---|
| รายจ่ายทั้งหมด | 181 | ข้อมูลเดิมก่อนนำการเปลี่ยนแปลงนี้ขึ้นใช้ |
| ยอดรวมต่างจากผลรวมรายการย่อย | 35 | ต้องตรวจบิล รวม VAT ส่วนลด และการแก้ย้อนหลัง ความต่างยังไม่ใช่ข้อสรุปว่าบัญชีผิด |
| วันของค่าตอบแทนที่จ่ายแล้วแต่ไม่มีลิงก์รายจ่าย | 37 | ตรวจยอดเดิมแล้วใช้ “ลงรายจ่ายจากยอดเดิม” อย่าสร้างรายเดือนทับ |
| ลิงก์ค่าตอบแทนชี้ไปยังรายจ่ายที่ไม่พบแล้ว | 1 | ระบบใหม่เตือนและให้บันทึกจากยอดจ่ายเดิมได้ |
| รายวันซ้ำกับรายจ่ายสรุปรายเดือน | 0 | ยังไม่พบในข้อมูลนี้ แต่ปิดช่องทางสร้างยอดรายเดือนซ้ำไว้แล้ว |
| รายจ่ายที่ยังไม่เชื่อมทะเบียนผู้รับเงิน | 121 | ต้องเลือกผู้รับเงินที่ถูกต้อง ห้ามเดาจากชื่อพนักงานอย่างเดียวเพราะมีชื่อซ้ำ |
| พนักงานที่ใช้งานแต่ยังไม่มีฐานเงินหรือเรต OT | 1 | ต้องตั้งค่าเรตก่อนยืนยันจ่าย OT |

รันตรวจซ้ำได้ด้วย `npx tsx scripts/audit-finance-legacy.ts` สคริปต์มีเฉพาะ SELECT ไม่ซ่อมหรือแก้ยอดอัตโนมัติ

## สิ่งที่เปลี่ยน

### รายจ่าย

- มือถือและเดสก์ท็อปใช้ฟอร์มเดียวกัน เพิ่ม ลบ หรือแก้จำนวน/ราคาจะรวมยอดอัตโนมัติ
- ฝั่งเซิร์ฟเวอร์คำนวณใหม่ด้วยหน่วยสตางค์ ไม่เชื่อยอดรายการที่ส่งมาจากหน้าจอ
- แยกไม่มี VAT / ราคารวม VAT / ราคายังไม่รวม VAT ส่วนลด และยอดหัก ณ ที่จ่ายตามเอกสาร
- ยอดเอกสาร = ยอดหลังส่วนลดบวก VAT เมื่อเป็นราคาไม่รวม VAT; จ่ายสุทธิ = ยอดเอกสารลบหัก ณ ที่จ่าย
- แยกวันที่ลงรายจ่าย วันที่เอกสาร เลขเอกสาร วันที่จ่ายจริง และวิธีจ่าย
- บันทึกฉบับร่างได้ รายการร่างและยกเลิกไม่นับในยอดยืนยัน และไม่อยู่ใน CSV ส่งบัญชี
- ข้อมูลเก่าคงยอดเดิมในโหมด LEGACY จนผู้ใช้ตรวจบิลและเลือกวิธีคำนวณใหม่ เพื่อไม่แก้บัญชีย้อนหลังโดยไม่ตั้งใจ
- เอกสารจากค่าตอบแทนแก้ยอดผ่านค่าตอบแทนเท่านั้น แนบหลักฐาน/แก้หมายเหตุได้ในหน้ารายจ่าย

### ทะเบียนผู้รับเงิน

- แยกร้านค้า/บริษัท บุคคล และพนักงาน พนักงานเชื่อมด้วย staff ID
- มีชื่อเรียก ชื่อตามเอกสาร เลขภาษี ที่อยู่ สาขาภาษี โทรศัพท์ ธนาคาร เลข/ชื่อบัญชี หมวดประจำ หมายเหตุ และสถานะใช้งาน
- เจ้าของเพิ่ม แก้ และปิดใช้งานได้จากเมนูผู้รับเงิน
- เก็บสำเนาข้อมูลผู้รับเงินบนเอกสาร การแก้ทะเบียนไม่ทับข้อมูลเอกสารเดิม หากต้องเติมข้อมูลบนบิลเก่า เจ้าของเลือกใช้ข้อมูลล่าสุดแล้วบันทึกพร้อมประวัติได้
- ไม่รวม/เดาผู้รับเงินเดิมที่สะกดคล้ายกันโดยอัตโนมัติ

### ค่าตอบแทนและ OT

- หน้าเดียวแสดงเวลาเข้า–ออกจริง กะตามแผน บุ๊กกิ้ง บริการเสริม ที่มาค่ามือ ทิป ยอดปรับ และยอดจ่าย
- ใช้เวลาเข้า–ออกที่ผู้ดูแลยืนยัน ไม่เอาตารางกะล่วงหน้ามาถือว่าเป็นเวลาทำงานจริง
- เกณฑ์เริ่ม OT เป็นรายคน: 540 นาที; พี่พร 600 นาที โดย migration ใช้ ID ที่ตรวจพบ ไม่จับคู่ชื่อคล้ายกัน
- เวลา OT = max(0, นาทีทำงานหลังหักเวลาพักที่ระบุ − นาทีปกติ) รองรับข้ามวัน ไม่เกิน 24 ชั่วโมง
- ค่าเริ่มต้นเวลาพักที่ไม่นับ = 0 ให้ปรับได้ เกณฑ์ชั่วโมงปกติและเรต OT แก้ได้ในตั้งค่าค่าตอบแทน
- รักษาเรตเดิม: ถ้ากำหนดเรตไว้ใช้เรตนั้น มิฉะนั้นเงินเดือน/240 หรือค่าแรงรายวัน/8 พี่พรตั้งไว้ 120 บาท/ชม.
- เปลี่ยน OT เป็นกำหนดเอง หรือใส่ยอดปรับเพิ่ม/ลดได้พร้อมเหตุผล รายการเดิมที่กรอก OT เองยังรักษาค่าเดิม
- ค่ามือยังเป็นกติกาเดิม: งาน COMPLETED ของช่างหลัก; ผู้ช่วยแสดงให้ตรวจแต่ไม่คิดค่ามือซ้ำ
- “ยืนยันจ่ายและบันทึกรายจ่าย” ใช้ธุรกรรมเดียว ป้องกันกดพร้อมกัน/กดซ้ำ และตรวจว่าข้อมูลต้นทางยังตรงกับที่เจ้าของเพิ่งตรวจ
- ยอดจ่ายแล้วเก็บรายละเอียดและเรต ณ ตอนจ่าย การเปลี่ยนบุ๊กกิ้งภายหลังไม่ทับยอดจ่าย
- เปิดแก้รายการจ่ายแล้วต้องมีเหตุผล ยกเลิกเอกสารเดิมและสร้างฉบับแก้ไขเมื่อยืนยันใหม่ เก็บประวัติผู้ทำรายการ
- การลงรายจ่ายจากยอด PAID เก่าไม่คำนวณเงินใหม่ และไม่สร้างวันจ่ายย้อนหลังที่ไม่มีในข้อมูล
- รายเดือนรวมค่ามือ OT ทิป และยอดปรับจากรายการรายวัน ไม่มีปุ่มลงรายจ่ายรายเดือนซ้ำ

### รายงาน

- เลือกสาขา ช่วงวันที่ และพนักงานได้
- รายงานบนหน้าจอแสดงเวลาทำงาน รายละเอียดงาน ค่ามือ OT ทิป ยอดปรับ และสถานะจ่าย
- ดาวน์โหลด CSV แยกสรุปรายวันกับรายละเอียดงานได้ หรือคัดลอกข้อความสรุป / พิมพ์เป็น PDF จากเบราว์เซอร์
- CSV ส่งบัญชีส่งออกทุกรายจ่ายที่ยืนยันในช่วงที่เลือก ไม่จำกัดตามจำนวนแถวที่หน้ารายการแสดง พร้อมลิงก์หลักฐานและช่องสิ่งที่ต้องตรวจ
- CSV ป้องกันข้อความถูกอ่านเป็นสูตรสเปรดชีต
- ยังไม่มีการส่ง LINE/email อัตโนมัติ รายงานเตรียมไว้ให้เจ้าของเลือกส่งเอง
- ฐานเงินเดือน/ค่าแรงแสดงเป็นข้อมูลอ้างอิงและยังจ่ายแยกตามรอบ ไม่ควรตีความยอดค่ามือ+OT+ทิปเป็นสลิปเงินเดือนครบภาษี/ประกันสังคม

## ก่อนส่งข้อมูลบัญชี

1. ตรวจ 35 รายการที่ยอดรายการไม่ตรงกับยอดบิล และ 37 วัน PAID ที่ยังไม่ลงรายจ่าย โดยเทียบหลักฐานเดิม
2. เชื่อมผู้รับเงินที่ถูกคน เติมชื่อตามเอกสาร เลขภาษี ที่อยู่ และข้อมูลบัญชีธนาคารตามความจำเป็น
3. เติมวันที่/เลขเอกสาร วิธีและวันที่จ่าย พร้อมแนบบิลหรือหลักฐานรับเงินและหลักฐานโอน
4. ให้ผู้ทำบัญชีตรวจประเภทภาษี VAT และหัก ณ ที่จ่ายตามกิจการ/เอกสารจริง ระบบนี้ไม่ได้เลือกอัตราภาษีตามสถานะกฎหมายให้เอง
5. ส่ง CSV เฉพาะรายการยืนยัน พร้อมเอกสารประกอบ รายการที่ช่อง “สิ่งที่ต้องตรวจ” ยังมีข้อความควรตรวจให้ครบก่อนถือว่าพร้อมลงบัญชี

ข้อมูลผู้รับเงินและหลักฐานรับเงินอ้างอิงแนวทางเอกสารประกอบรายจ่ายของ [กรมสรรพากร](https://www.rd.go.th/31914.html) การครบช่องในระบบไม่ใช่การรับรองสิทธิทางภาษี

## การนำขึ้นใช้และทดสอบ

- Migration: `prisma/migrations/20260913120000_connected_finance/migration.sql` เป็นการเพิ่มตาราง/คอลัมน์ พร้อมตั้งชั่วโมงปกติของพี่พร ไม่ลบหรือเปลี่ยนยอดเดิม
- รัน migration ก่อนนำโค้ดใหม่นี้รับคำขอ ฐานข้อมูลจริงยังไม่ได้เปลี่ยนในการทำงานรอบนี้
- ขั้นตอน build ปกติของโครงการใช้ `prisma migrate deploy` อยู่แล้ว ต้องนำ schema และ migration ไปด้วยกัน ห้ามใช้ db push
- ตรวจการอัปเกรดกับฐานข้อมูลทดสอบก่อน deploy; ห้ามรัน fixtures กับฐานข้อมูลจริง
- `npm run test:finance`: กฎเงิน วันที่ และเวลา
- Integration test: ใช้ฐานข้อมูล localhost ชื่อ `errday_finance` เท่านั้น ตั้ง DATABASE_URL ให้ฐานนั้น แล้วเปิดแอปด้วยค่าเดียวกันที่พอร์ต 3087 ก่อนรัน `npm run test:finance:integration`
- มี Prisma PostgreSQL adapter สำหรับ localhost เพื่อแยกการทดสอบจาก Neon ที่ใช้งานจริง
- ใช้ NEXT_DIST_DIR แยกผล build/preview จากเซิร์ฟเวอร์พัฒนาตัวอื่น
- การทดสอบครอบคลุมสิทธิ์เจ้าของ การกดจ่ายพร้อมกัน/ซ้ำ การ rollback การเปลี่ยนต้นทางระหว่างตรวจ การเปิดแก้/ยกเลิก ยอดเก่า ลิงก์รายจ่ายหาย OT 9/10 ชั่วโมง การรวมทิป ข้อมูลผู้รับเงิน และการส่งออก
- ตรวจ migration ทั้งติดตั้งฐานข้อมูลใหม่และอัปเกรดจาก schema เดิมใน PostgreSQL จำลองแล้ว ยอดเก่ายังคงเดิมและเกณฑ์ 9/10 ชั่วโมงถูกต้อง
- ตรวจหน้าจอรายจ่ายบนมือถือและเดสก์ท็อป รวมถึงคำนวณจำนวน × ราคา, VAT, ส่วนลด และหัก ณ ที่จ่ายผ่านเบราว์เซอร์แล้ว

การเปลี่ยนแปลง Dashboard/Visitor forecast ที่มีอยู่ก่อนเริ่มงานนี้ไม่ได้เป็นส่วนของงานการเงินนี้
